# ADR-001: Extract the Dispatch Service from the Monolith

**Status:** Accepted
**Date:** 2026-09-11
**Deciders:** System Architect (agent), Backend/Platform Lead (agent)

## Context

SALIS AUTO is evolving from a single-tenant-per-garage ERP monolith into a
multi-service "super app" (garage booking, parts, roadside/towing, fleet,
insurance, rentals, ride-share — see `shared/schema/` for the shared-rail
schema already landed: Identity, Wallet/Ledger, Payments, Catalog, Orders,
Notifications, plus the Fleet domain).

The locked architecture decision (captured earlier in planning) is:
**"modular monolith first; extract the dispatch engine to its own service
first."** Every future mini-app that assigns work to a person or vehicle —
garage job cards today, fleet trips and roadside tow requests tomorrow,
ride-share later — needs the same underlying capability: given a task and a
set of candidates, pick the best match and record why.

Today that capability exists only as monolith-internal code:
- `server/services/scheduling-optimizer.ts` — pure, already-tested scoring
  function (skills match, availability, load balance, efficiency). No I/O.
- `server/services/assignmentAI.ts` — OpenAI-backed recommendation engine for
  garage job cards specifically; reads/writes through `storage` (the
  monolith's DB layer) and is coupled to `JobCard`/`TechnicianProfile` types.
- `server/engine/event-bus.ts` — in-process pub/sub, explicitly documented as
  "upgradeable to Redis/RabbitMQ for distributed deployments" — i.e. already
  designed with extraction in mind.

None of this is reusable by fleet/roadside/ride today because it's shaped
around garage job cards and lives inside the monolith's process and database.

## Decision

Extract a **Dispatch service** (`services/dispatch/`) as a physically
separate, independently deployable Node/Express/TypeScript service. It owns
one bounded context: **"given a task and a list of candidates, produce and
record an assignment decision."**

### Bounded context

**Dispatch owns:**
- `assignment_requests` — a task description + a resolved candidate list, as
  submitted by a caller
- `assignment_decisions` — the scored/ranked outcome, with rationale
- `dispatch_events` — audit trail of decisions (append-only)

**Dispatch does NOT own:**
- Technicians, drivers, vehicles, job cards, fleet trips, garages — these
  stay in the monolith's tables (`users`, `technicianProfiles`, `jobCards`,
  `fleetDrivers`, `fleetVehicles`, `fleetTrips`, …). Dispatch never queries
  the monolith's database directly (no shared schema).

This keeps Dispatch's data model generic (`Candidate`, `Task`) rather than
coupled to "technician" or "job card" — the same service serves garage job
assignment, fleet trip/driver assignment, and (later) roadside/ride matching
without forking logic per mini-app.

### Communication pattern

**Caller resolves candidates, Dispatch only scores.** The monolith (or any
future mini-app backend) already knows its own candidates (technicians on
duty, drivers under a fleet account, tow operators in range) — it queries its
own DB for them and sends the resolved list to Dispatch. This avoids Dispatch
needing synchronous reverse calls into the monolith to look up entities,
which would create a chatty, tightly-coupled interface and violate "no
shared database between services."

- **Sync REST, `POST /v1/assignments`** — scoring today is pure CPU
  (skills/load/efficiency math), sub-100ms, so a synchronous call fits the
  communication guardrail (only sub-100ms query/command pairs go sync).
  Request: `{ taskType, requirements, candidates[] }`. Response: ranked
  decision + rationale, persisted before the response is returned.
- **Future, once geo/ETA (PostGIS) enters the picture** (fleet trip
  dispatch, roadside, ride-share): scoring will involve routing/ETA lookups
  that are no longer sub-100ms. At that point Dispatch will accept the
  request synchronously (202 Accepted), compute asynchronously, and emit a
  `dispatch.assignment.decided` event. The event contract is already
  reserved (`dispatch_events` table + `eventPublisher` interface in
  `src/lib/eventPublisher.ts`) so this is a config change, not a redesign,
  when a broker (Redis Streams/RabbitMQ) is provisioned.
- **Resilience:** the monolith calls Dispatch through
  `server/clients/dispatchClient.ts`, which wraps every call in a timeout,
  a small retry budget, and a circuit breaker with a **local fallback** —
  if Dispatch is unavailable, the caller falls back to
  `scheduling-optimizer.ts`'s in-process scoring so garage/fleet operations
  never hard-fail on a Dispatch outage during the strangler-fig period.
- **Correlation IDs:** every request into Dispatch carries `x-correlation-id`
  (generated by the monolith if absent), logged on both sides, so a request
  can be traced end-to-end even across the process boundary.

### Data ownership & consistency

Database-per-service: Dispatch has its own Postgres schema/connection
(`services/dispatch/src/schema.ts`, own `DISPATCH_DATABASE_URL`), decoupled
from the monolith's `shared/schema.ts`. An `assignment_decision` references
the monolith's entity only by an opaque `(entityType, entityId)` pair — no
foreign key across the boundary. Consistency is eventual and one-directional:
the monolith is the source of truth for "did this assignment actually get
applied" (it writes `assignedTechnicianId` / `driverId` itself, after reading
Dispatch's decision) — Dispatch is only ever a decision-support system, never
the system of record for who is doing what. This keeps the migration
reversible: if Dispatch is rolled back, the monolith's own data is untouched.

### Migration plan (strangler fig — no rewrite required on day one)

1. **New consumers start on Dispatch immediately.** Fleet trip/driver
   assignment (`server/routes/fleet.routes.ts`) is the first real caller —
   it has no legacy assignment logic to migrate, so it calls
   `dispatchClient.requestAssignment()` from day one
   (`POST /api/fleet/accounts/:accountId/dispatch/assign`).
2. **Existing garage job-card assignment is untouched for now.**
   `assignmentAI.ts` keeps serving `/api/jobcards/:id/ai-recommendations` as-is.
   It is not rewritten or migrated in this change.
3. **Future step (not in this change):** once Dispatch has proven itself on
   fleet traffic, `assignmentAI.ts`'s non-AI scoring path can be pointed at
   Dispatch behind a feature flag, with the OpenAI rationale layer staying in
   the monolith (Dispatch does deterministic scoring; the LLM narrative
   wrapper is a monolith concern, not a Dispatch concern).
4. **`scheduling-optimizer.ts` stays in the monolith** as the circuit-breaker
   fallback (see above) — it is not deleted.

### Deployment

- `services/dispatch/Dockerfile` — standalone image, own `package.json`.
- `docker-compose.yml` gains a `dispatch` service (already-provisioned
  Postgres reused via a second database, `salis_dispatch`).
- `k8s/dispatch/` — Deployment + Service + liveness/readiness probes
  (`/health/live`, `/health/ready`) for when this moves off Compose. Not
  wired to a live cluster in this change; manifests are prepared ahead of
  need, matching the "extract dispatch first" sequencing already agreed.

## Consequences

**Positive:** one dispatch/matching capability shared by every current and
future mini-app instead of a fork per service; the monolith is not blocked
on this service being perfect (fallback); event contract is reserved for
when scoring needs to go async (geo/ETA).

**Negative:** one more service to run, deploy, and monitor; a network hop
(with a timeout/retry/breaker budget) is now on the fleet-dispatch path
where there was none before; correlation-ID discipline must be maintained by
every future caller.

**Not done in this change:** no message broker is provisioned; no live K8s
cluster is targeted; garage job-card assignment is not migrated.
